# Архитектура

Система состоит из двух независимых частей:

- **Транспорт.** Протокол `fedarisha` в [Xray-core-fedarisha](https://github.com/Fedarisha/Xray-core-fedarisha). Он умеет передавать трафик через бакет между outbound клиента и inbound ноды. О панели он ничего не знает: ему нужны бакет, ключи и список разрешённых пользователей.
- **Управление.** Форки Remnawave (backend, node, frontend, subscription-page). Они выпускают каждому пользователю отдельный S3-ключ, поддерживают список пользователей на нодах и отдают клиентам готовый конфиг.

## Компоненты

```
                     ┌──────────────────────────── панель ────────────────────────────┐
  клиент ── GET ──►  │ subscription-page ──► backend ── Postgres (кеш ключей в user_meta)│
  (v2rayN/NG)        └──────────────────────────────┬─────────────────────────────────┘
      │                                             │ mTLS + JWT: /node/fedarisha/*,
      │                                             │ старт Xray, добавление пользователей
      │                                             ▼
      │                                  ┌──────── нода ────────┐
      │                                  │ node (NestJS)         │── IAM/PAK API ──► провайдер S3
      │                                  │ xray + inbound        │
      │                                  │   fedarisha           │◄── webhook ────── провайдер S3
      │                                  └──────────┬────────────┘
      │           S3: PUT / GET / LIST / DELETE     │
      └──────────────────► бакет ◄──────────────────┘
```

| Компонент | Роль в fedarisha |
| --- | --- |
| Xray на клиенте | Outbound `fedarisha`: пишет `c_*`, читает `s_*` в папке пользователя, ключ пользователя. |
| Xray на ноде | Inbound `fedarisha`: сканирует бакет, делает рукопожатие, выпускает трафик в интернет. Работает с мастер-ключом. Webhook-сервер тоже поднимает Xray. |
| node | Выпускает, отзывает и проверяет ключи пользователей (`/node/fedarisha/*`). Добавляет и удаляет пользователей в работающем Xray, как для других протоколов. Собственного состояния не хранит. |
| backend | Хранит выпущенные ключи, реагирует на события пользователей, подставляет ключ пользователя в outbound подписки, заполняет `clients` и значения webhook по умолчанию в конфиге ноды. |
| frontend | Редактор конфиг-профилей. Встроенный WASM-валидатор Xray не знает `fedarisha`, поэтому перед проверкой такие инбаунды заменяются заглушками. |
| subscription-page | Пропускает тип клиента `fedarisha-json`. |

## Путь пользователя

Пусть в конфиг-профиле есть инбаунд `fed-eu` с `storage.prefix = "fed"` и `authType = "vkcloud-pak"`, он включён на ноде и входит во внутренний сквад. Администратор создаёт пользователя с id `42` и добавляет его в этот сквад.

1. **Xray на ноде узнаёт о пользователе.** Как и для остальных протоколов, backend вызывает стандартное API ноды для добавления пользователя. Нода добавляет в инбаунд `fed-eu` пользователя с `email = "42"`. При полном перезапуске Xray тот же пользователь приходит в `settings.clients` (`{"id": "42", "email": "42"}`).
2. **Выпуск ключа.** Для нового пользователя ключ выпускается при первом запросе подписки (шаг 5). Кроме того, на события `user.enabled`, `user.modified` и `user.traffic_reset` у активного пользователя backend заранее выпускает ключи для всех fedarisha-инбаундов из его сквадов, для которых ключа ещё нет. Для этого backend вызывает на ноде `POST /node/fedarisha/provision-user` с `prefix = "fed/42/"`.
3. **Нода выпускает ключ.** Нода берёт мастер-ключ из конфига своего Xray и выпускает у VK Cloud ключ `<id>-<хеш тега>` с доступом только к `fed/42/`.
4. **Backend сохраняет ключ** в `user_meta.metadata.fedarisha["fed-eu"]`.
5. **Клиент запрашивает подписку** `https://sub.example.com/<shortUuid>/fedarisha-json`. Backend строит Xray JSON. Для хоста на инбаунде `fed-eu` в outbound попадают `bucket`, `endpoint`, `region`, `sessionsDir` и `tuning` из инбаунда, а также `prefix = "fed/42/"` и ключ пользователя. Сохранённый ключ сначала проверяется через ноду. Если ключа нет или он недействителен, новый выпускается прямо во время запроса (шаги 3–4).
6. **Клиент подключается.** Клиент пишет `fed/42/sessions/<id>/c_hello`. Нода видит сессию, проверяет, что `42` есть среди пользователей инбаунда, и отвечает `s_ack`. Дальше данные идут, как описано в [protocol.md](protocol.md).
7. **Пользователь отключён или истёк.** На `user.disabled`, `user.limited`, `user.expired` и `user.deleted` backend отзывает все ключи пользователя через ноду и удаляет их из кеша. Параллельно стандартный механизм Remnawave удаляет пользователя из Xray, и нода закрывает его открытые сессии.

Подробности, таймауты и обработка ошибок: [panel-integration.md](panel-integration.md).

## Где хранится состояние

| Где | Что |
| --- | --- |
| Postgres панели, `user_meta.metadata.fedarisha` | Выпущенные ключи: `{accessKey, secretKey, prefix, configProfileUuid, issuedAt}` по тегу инбаунда. |
| Конфиг-профиль панели | Инбаунд с мастер-ключами и параметрами провайдера. Уходит на ноду при старте Xray. |
| Аккаунт провайдера S3 | Сами ключи (PAK в VK Cloud, сервисные пользователи в Selectel). |
| Бакет, `.fedarisha-pak-state/` | Список участников bucket policy (только `selectel-iam`). |
| Бакет, `<prefix>/<id>/sessions/` | Файлы активных сессий. |
| Бакет, правила жизненного цикла | `fedarisha-expire-<prefix>`: удаление объектов старше суток. |
| Память Xray на ноде | Список пользователей инбаунда и открытые сессии. |

Нода не хранит, какой ключ кому выдан. Если кеш в панели потерян, при следующем выпуске провайдер сообщит, что ключ уже существует, и нода пересоздаст его.

## Безопасность

От чего защищает система:

- **Чужие папки.** С `vkcloud-pak` и `selectel-iam` ключ пользователя даёт доступ только к его папке. Это обеспечивает провайдер S3.
- **Отключённые пользователи.** Нода не отвечает на рукопожатие, если пользователя нет в списке инбаунда, и закрывает его сессии при удалении. Это работает, даже если ключ ещё не отозван или отзыв не удался.
- **Чтение бакета посторонним.** Содержимое файлов зашифровано AES-256-GCM с ключом, который выводится при рукопожатии и нигде не сохраняется. Доступ к бакету только на чтение, в том числе у провайдера, не раскрывает трафик.

От чего не защищает:

- **Активная атака с правом записи в папку пользователя.** Рукопожатие X25519 не аутентифицировано: клиент не может проверить, что `s_ack` написала именно нода. Тот, кто может писать в папку пользователя, может встать посередине. Такое право есть у провайдера S3, у владельца мастер-ключа, а в режиме `static` — у любого пользователя.
- **Метаданные.** Провайдер видит, какой ключ, когда и сколько данных пишет в бакет.
- **Блокировка самого хранилища.** Транспорт можно заблокировать только вместе с доменом хранилища. Это его основная идея, а не гарантия.

Мастер-ключи хранятся в конфиг-профиле панели и в конфиге Xray на ноде, клиентам они не передаются. Исключение — режим `static`: там клиенты получают мастер-ключ.
