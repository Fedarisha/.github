# Протокол

Описание того, как клиент и нода обмениваются данными через бакет. Документ описывает текущий код в [`proxy/fedarisha/`](https://github.com/Fedarisha/Xray-core-fedarisha/tree/main/proxy/fedarisha) и не зависит от панели.

## Раскладка бакета

```
<bucket>/
└── <basePrefix>/                     storage.prefix инбаунда
    ├── <user>/                       storage.prefix клиента = <basePrefix>/<user>/
    │   └── sessions/                 storage.sessionsDir
    │       └── <sessionId>/
    │           ├── c_hello           клиент → нода, рукопожатие
    │           ├── s_ack             нода → клиент, рукопожатие
    │           ├── c_00000000 …      данные клиент → нода
    │           └── s_00000000 …      данные нода → клиент
    └── <user>/…
```

- `<user>` — идентификатор пользователя. Нода считает первый сегмент пути после своего `prefix` именем пользователя и сверяет его со списком `clients` инбаунда. В панели это числовой id пользователя.
- `<sessionId>` — 16 случайных байт в hex, 32 символа.
- Имена файлов данных: `c_` или `s_` и порядковый номер в hex, дополненный нулями до 8 знаков. Клиент пишет только `c_*`, нода только `s_*`.

Если `sessionsDir` не задан, используется `sessions`. Менять его не стоит: webhook распознаёт сессии только по сегменту пути `sessions`.

## Рукопожатие

Сертификатов нет. Нода не проверяет клиента криптографически. Доступ определяется тем, может ли клиент писать в папку пользователя (S3-ключ), и тем, есть ли этот пользователь в `clients` инбаунда.

1. **Клиент** генерирует `sessionId` и пару ключей X25519 и кладёт `<sessionsDir>/<sessionId>/c_hello`:
   ```
   sessionId (32 байта ASCII-hex) || clientPublic (32 байта)
   ```
2. **Нода** находит новую папку сессии и проверяет, что `<user>` есть в списке разрешённых пользователей. Если его нет, нода удаляет `c_hello` и больше не трогает сессию. Если есть, нода читает `c_hello`, удаляет его, генерирует свою пару X25519 и пишет `s_ack` с телом `serverPublic` (32 байта).
3. **Клиент** читает `s_ack` каждые 500 мс в течение 60 секунд, затем удаляет его. Если ответа нет, клиент удаляет `c_hello` и возвращает ошибку.

Обе стороны вычисляют ключ:

```
shared = X25519(ownPrivate, peerPublic)
key    = HKDF-SHA256(ikm = shared, salt = sessionId, info = "fedarisha-e2e-v1"), 32 байта
AEAD   = AES-256-GCM(key)
```

`salt` здесь — ASCII-строка `sessionId`, а не исходные байты.

## Файл данных

Каждый файл `c_<seq>` или `s_<seq>` — один шифротекст AES-256-GCM:

```
nonce (12 байт) = direction[0:2] || 0x00 0x00 || uint64_be(seq)     direction = "c_" или "s_"
aad             = sessionId (ASCII)
plaintext       = flag (1 байт) || payload
```

- `flag = 0x01`: `payload` сжат deflate (уровень BestSpeed). `flag = 0x00`: `payload` без сжатия. Сжатие применяется, только если результат меньше исходного.
- Пара `(direction, seq)` уникальна в пределах сессии, поэтому nonce не повторяются.
- Размер одного файла ограничен `maxFileSizeBytes` (по умолчанию 2 MiB). Более крупный буфер режется на несколько файлов с последовательными номерами.

## Поток внутри сессии

Расшифрованные файлы, склеенные по порядку номеров, образуют непрерывный байтовый поток. Поверх него работает [yamux](https://github.com/hashicorp/yamux). Клиентский outbound держит одну yamux-сессию на все соединения и открывает её заново, если она закрылась.

Параметры yamux на обеих сторонах: keepalive каждые 10 с, таймаут ответа на keepalive 30 с, окно потока 64 MiB, `StreamOpenTimeout` отключён.

Каждый yamux-поток начинается с заголовка назначения:

```
uint16_be  len | 0x8000, если UDP       длина host, не более 512
host       len байт                     IP или домен в текстовом виде
uint16_be  port
```

Для TCP дальше идёт обычный двунаправленный поток. Для UDP каждый пакет упаковывается так:

```
uint16_be  metaLen
meta       metaLen байт: 0x02 || адрес и порт в формате xudp       (если metaLen > 0)
uint16_be  payloadLen
payload
```

## Запись и чтение

Запись буферизуется: буфер уходит в S3 каждые `writeIntervalMs` (по умолчанию 20 мс) или сразу, когда достигает `maxFileSizeBytes`. Файлы загружаются параллельно, поэтому в бакете они могут появиться не по порядку. Зависшие PUT и GET повторяются на новом соединении.

Чтение идёт в цикле: LIST папки сессии, GET найденных файлов начиная с ожидаемого номера, расшифровка и выдача строго по порядку. Прочитанный файл сразу удаляется. Файлы, пришедшие после пропуска в нумерации, ждут в памяти. Если пропуск не заполняется 7 секунд, сессия закрывается, и клиент открывает новую.

Пауза между пустыми опросами зависит от того, как давно приходили данные:

| С последнего полученного файла | Пауза |
| --- | --- |
| меньше 5 с | 90 мс |
| 5–30 с | 300 мс |
| больше 30 с | 700 мс |

Если на ноде включён webhook, она после пустого опроса ждёт уведомления о новом файле и делает страховочный опрос раз в 30 с. Клиент всегда опрашивает по таблице.

## Обнаружение новых сессий на ноде

Без webhook нода каждые 500 мс делает LIST `<basePrefix>/`, получает список пользователей и для каждого делает LIST `<user>/<sessionsDir>/`. Это 1 + N запросов LIST за цикл, где N — число папок пользователей в бакете.

С webhook интервал такого сканирования увеличивается до 10 с, а новые сессии обрабатываются сразу по уведомлению о создании `c_hello`.

## Webhook

Нода поднимает HTTP(S)-сервер на `webhook.listen` и принимает POST в формате S3 event notification:

```json
{ "Records": [ { "s3": { "bucket": { "name": "…" }, "object": { "key": "<basePrefix>/<user>/sessions/<id>/<file>" } } } ] }
```

- Если `<file>` — `c_hello`, нода запускает рукопожатие для этой сессии.
- Для любого другого файла нода будит цикл чтения этой сессии.

При `autoSetup: true` нода на старте регистрирует уведомление `s3:ObjectCreated:Put` на `publicUrl` через `PUT /?notification` с `SimpleTopicConfiguration`. Это расширение API VK Cloud. Регистрация перезаписывает конфигурацию уведомлений бакета. Если регистрация не удалась, в лог пишется предупреждение, а инбаунд продолжает работать через опрос.

VK Cloud при регистрации отправляет `SubscriptionConfirmation`. Нода отвечает подписью:

```
signature = hex(HMAC(HMAC(HMAC(Token, Timestamp), TopicArn), publicUrl))
```

Здесь `HMAC(k, m)` — HMAC-SHA256 с ключом `k`. Поэтому `publicUrl` должен быть доступен провайдеру уже в момент старта ноды.

Несколько инбаундов могут делить один `listen`, если у них одинаковые настройки TLS. Если у них к тому же совпадает путь в `publicUrl`, то `publicUrl` должен совпадать целиком, а их `prefix` не должны пересекаться. Такие инбаунды получают все уведомления по этому пути, и каждый выбирает свои по префиксу. Иначе инбаунд не стартует.

## Завершение и очистка

| Что | Когда удаляется |
| --- | --- |
| Прочитанный файл данных | Сразу после чтения |
| `c_hello`, `s_ack` | Сразу после обработки |
| Остатки сессии | При закрытии соединения. Выполняется LIST папки и `DeleteObjects` пачками по 1000 ключей (или поштучный DELETE, если хранилище его не поддерживает), лимит 60 с |
| Брошенные сессии | Правило жизненного цикла бакета |

На старте инбаунд добавляет в бакет правило жизненного цикла `fedarisha-expire-<prefix>`: удалять объекты под `prefix` через 1 день. Правила для других префиксов сохраняются. Если `prefix` пустой, правило не ставится.

Сессия закрывается, если за `idleTimeoutSec` (по умолчанию 300 с) не пришло ни одного файла. Keepalive yamux приходит каждые 10 с, поэтому живая сессия по этому таймауту не закрывается.

Когда пользователя удаляют из инбаунда (через API Xray), нода сразу закрывает все его активные yamux-сессии. Новые рукопожатия для него отклоняются.
