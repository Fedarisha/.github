# Провайдеры ключей

При работе через панель каждому пользователю нужен свой S3-ключ, который даёт доступ только к его папке `<prefix>/<id>/`. Ключи выпускает нода, используя мастер-ключи из конфига инбаунда. Способ выпуска задаёт поле `storage.authType`.

| `authType` | Как выпускается ключ | Изоляция пользователей |
| --- | --- | --- |
| `vkcloud-pak` | Prefix Access Key в VK Cloud, один запрос к S3 | Да, на стороне S3 |
| `selectel-iam` | Сервисный пользователь IAM и bucket policy в Selectel | Да, на стороне S3 |
| `static` | Никак, всем отдаётся мастер-ключ | Нет |

`authType` нужен только панели. Xray его игнорирует, а в подписку клиенту он не попадает. Если `authType` не задан или задан другим значением, нода отвечает ошибкой на запросы выдачи ключей.

Код провайдеров: [`node/src/modules/fedarisha-pak/`](https://github.com/Fedarisha/node/tree/main/src/modules/fedarisha-pak).

## Имя ключа

У провайдера ключ пользователя называется так:

```
<id пользователя>-<первые 8 hex-символов sha1(inboundTag)>
```

Хеш тега нужен, потому что в VK Cloud имена ключей уникальны в пределах всего аккаунта, а не бакета. Без него два инбаунда на одном аккаунте с разными бакетами конфликтовали бы.

Если при выпуске провайдер сообщает, что ключ с таким именем уже есть (например, панель потеряла кеш), нода удаляет старый ключ и создаёт новый.

## Проверка ключа

Чтобы проверить, что выданный ключ ещё действует, нода выполняет с этим ключом PUT пустого объекта `<prefix>.rw-pak-probe-<время>-<uuid>`, затем HEAD и DELETE. Ответы 2xx означают, что ключ действует. 403 или 404 — что ключ недействителен. Любой другой ответ считается сбоем, и ключ не трогают.

## `vkcloud-pak`

```json
"storage": {
  "type": "s3",
  "authType": "vkcloud-pak",
  "bucket": "my-bucket",
  "endpoint": "https://hb.ru-msk.vkcloud-storage.ru",
  "region": "ru-msk",
  "prefix": "fed",
  "accessKey": "<мастер-ключ>",
  "secretKey": "<мастер-секрет>"
}
```

Выпуск: `PUT https://<bucket>.<endpoint>/?pak&username=<имя>&prefix=<prefix>`, подписанный мастер-ключом. Отзыв: тот же запрос с методом `DELETE`. Используется [PAK API VK Cloud](https://cloud.vk.com/docs/ru/tools-for-using-services/api/api-spec/s3-rest-api/pak-api).

- Квота на число PAK считается на весь аккаунт и делится между всеми бакетами.
- Автонастройка webhook (`autoSetup`) работает только с VK Cloud.

## `selectel-iam`

```json
"storage": {
  "type": "s3",
  "authType": "selectel-iam",
  "bucket": "my-bucket",
  "endpoint": "https://s3.ru-1.storage.selcloud.ru",
  "region": "ru-1",
  "prefix": "fed",
  "accessKey": "<S3-ключ сервисного пользователя>",
  "secretKey": "<…>",
  "masterServiceUserId": "<IAM ID этого сервисного пользователя>",
  "iam": {
    "accountId": "123456",
    "projectName": "My Project",
    "projectId": "<uuid проекта>",
    "username": "<сервисный пользователь с ролью iam-admin>",
    "password": "<…>"
  }
}
```

- `accessKey` должен принадлежать сервисному пользователю IAM, а `masterServiceUserId` — это его IAM ID. Перед изменением policy нода проверяет, что ключ действительно принадлежит этому пользователю. S3-ключ пользователя панели Selectel здесь не подойдёт: такого пользователя нельзя указать в policy через API.
- В `iam` можно дополнительно задать `identityUrl` и `apiUrl`, если нужны адреса, отличные от стандартных.

При выпуске ключа нода:

1. Находит или создаёт сервисного пользователя с именем ключа и ролью `s3.user` на проект.
2. Добавляет его в bucket policy: доступ к объектам и LIST только внутри `<prefix>/<id>/`. Principal — IAM ID сервисного пользователя, другие формы Selectel не поддерживает.
3. Удаляет старые S3-ключи этого пользователя с тем же именем и создаёт новый.

При отзыве нода удаляет ключ. Если у сервисного пользователя не осталось ключей, нода удаляет и его, и его записи из policy.

Кроме пользователей, policy всегда разрешает мастер-пользователю LIST бакета и доступ к объектам под `prefix` инбаунда. Без этого Selectel запретил бы доступ и самой ноде: после установки policy он отказывает всем, кто в ней не указан.

Особенности:

- Selectel не отдаёт текущую policy даже владельцу. Поэтому нода хранит список участников в `<bucket>/.fedarisha-pak-state/<prefix>.json` и при каждом изменении перезаписывает policy целиком. Политики, заданные вручную, будут затёрты.
- Размер policy ограничен 20 KB, это меньше 100 пользователей на бакет. Больше пользователей можно разнести по нескольким инбаундам с разными бакетами.
- Запросы идут только в path-style.

## `static`

```json
"storage": {
  "type": "s3",
  "authType": "static",
  "bucket": "my-bucket",
  "endpoint": "https://minio.example.com",
  "region": "us-east-1",
  "prefix": "fed",
  "accessKey": "<общий ключ>",
  "secretKey": "<…>",
  "pathStyle": true
}
```

Все пользователи получают ключ из конфига. Выпуск и отзыв ничего не делают. Проверка считает ключ недействительным, если он не совпадает с ключом из конфига (например, после смены ключа в инбаунде).

`pathStyle` влияет только на проверку ключа нодой. Xray всегда работает в path-style.

Подходит для MinIO, Garage и других S3 без API выдачи ключей, а также для тестов. Изоляции нет: любой пользователь может читать и перезаписывать папки остальных, а значит, и вмешиваться в чужие сессии (см. [architecture.md](architecture.md#безопасность)).
